## Hardware attached
- **Follower arm** (SO-101): 12.1–12.2V servos, port `/dev/ttyACM*` via `usb-1a86_USB_Single_Serial_5A7C117109-if00`.
- **Leader arm** (SO-101): 7.2–7.3V servos, port via `usb-1a86_USB_Single_Serial_5A7C118584-if00`. Intermittently fails to enumerate on the shared USB hub — suspected power/bandwidth limit on the nested hub topology (kernel logs showed `usb ...-port3: cannot reset (err=-71)` during earlier overload).
- **Cameras**: "Generic HD video" (349c:3307, `/dev/video0`) — has working built-in mic (confirmed via `arecord`), usable resolution up to 2560×1440 MJPG, streamed live via `ustreamer --resolution=640x480 --desired-fps=10` on port 8080 (1280x720 crash-looped, 640x480 is stable). "Sunplus SPCA2085" (1bcf:0b09, `/dev/video2`) — wrist-mounted — **confirmed dead at the hardware/protocol level, not a config/power issue**: exhaustively tested via `fswebcam`, `ustreamer` (all resolutions incl. its native 160x120), raw `v4l2-ctl --stream-mmap` (hangs indefinitely with zero output), and re-tested identically on Windows via DirectShow (same driver family, `usbvideo.sys`, not a vendor driver as originally hoped) — every path produces either a stable black frame or a fixed one-line color-noise-then-black pattern, never real image data, deterministically across cable/port replug. Do not spend further debug time on this unit; replace it (OV5640-based UVC module available locally in VN via Hshop.vn/mlab.com.vn/pivietnam.com.vn; OV9782 global-shutter is the internationally-ordered ideal but not locally stocked).
- 2× Huasheng USB2.0 hubs, nested (hub B plugged into hub A). This nesting is the likely root cause of the recurring "second device won't enumerate" pattern. **Superseded 2026-08-14** by a Genesys Logic-chipset hub (proper USB2 4-port hub + USB3 hub w/ built-in AX88179 gigabit ethernet) — single hub, not nested, with its own power adapter now on a wall outlet (was previously mistakenly fed from a power bank, which likely under-delivers current under load spikes).
- **USB mic**: BOYAMIC (Actions Semiconductor, `10d6:b011`) — works, but only in a specific configuration found by trial: **S24_3LE format, 2 channels, 48000Hz, real signal on the RIGHT channel only (LEFT is silent)**; rejects 16-bit and mono requests outright (`arecord` errors "Sample format non available" / "Channels count non available"). ALSA capture gain is already fixed at 100% — there is no software gain knob to raise for this device.
- **Board's own USB-C port requires a genuine data-capable cable, not charge-only**: after a hub+mic rewiring session, `lsusb` briefly showed *zero* devices at all (not even the hub) despite the board itself staying up or (with a bad cable) even losing power - Arduino's own docs only generically warn to use "a USB-C dongle/cable with data capability," not charge-only. If a hub disappears entirely from `lsusb` after reseating a cable, suspect the cable before the hub.
- **Board-wide power crash** (root-caused): plugging in a 2nd camera while the follower arm + 1st camera + hub were already connected caused the *entire board* to lose power and reboot uncleanly (confirmed via `dmesg`/`systemd-journald` corruption messages showing a real early-boot log, not just a USB subsystem reset). Root cause: the UNO Q's single USB-C port both powers the board *and* back-feeds the downstream hub/device chain — total draw of 2 cameras + arm + hub exceeds what one port sustains; a stronger upstream supply alone did not fix it (the nested hub itself isn't independently powered).
  - Official spec (`docs.arduino.cc/tutorials/uno-q/power-specification/`): board draws a fixed **5V/3A (15W)** via USB-C PD — it only ever negotiates this one profile, never higher-voltage PD tiers, so a higher-wattage charger (e.g. a 65W GaN unit) provides *no* extra headroom on the 5V rail unless that specific charger's 5V rail itself exceeds 3A (check the printed spec table; most don't — the 65W is only reachable at 20V). Docs explicitly warn: "if the supply current-limits during peaks, voltage hang may cause resets" — matches the observed crash signature exactly.
  - Whether powering via the board's `+5V`/`VIN` header pins (JANALOG connector: `...→ +3V3 → +5V → GND → GND → VIN →...`) would free the USB-C port for host-only duty was investigated and **does not work as hoped**: per Arduino forum reports, powering via the header pins puts the USB-C controller into device mode by default, so it stops supplying VBUS to downstream hubs at all. Do not pursue this path — give the hub independent power instead (done, see above), keep the board itself on USB-C.

Full `lerobot-calibrate` still won't run here (needs torch/datasets/gymnasium/etc. that are deliberately absent) — use the two small standalone helper scripts below instead, which only touch the already-working `SO101Follower`/`bus` classes.

- **openWakeWord + Vosk** (`~/wakeword-env/`): used for on-device benchmarking (see PIPELINE.md for numbers). Not yet wired into `mira-robot`. Vosk was later abandoned project-wide in favor of Whisper/PhoWhisper (accent-recognition failures) — see `windows-pc.md`.
- **`camera_exporter.py`** (`/home/arduino/camera_exporter.py`, plain `python3`, stdlib only — no deps installed, by design, given the board's tight RAM): Prometheus-format `/metrics` on `:9101`, polls the overhead camera's `ustreamer` snapshot every 10s (`camera_up{camera="overhead"}`) and reports the wrist camera as a static known-broken gauge. Started via bare `nohup`, not a systemd service — will not survive a reboot.
- **Board-native voice pipeline** (`/home/arduino/board_wakeword.py`, added to `~/.local/share/mira-so101/venv/` on 2026-08-14: `openwakeword`, `sounddevice`, `onnxruntime`, `scipy`, `sherpa-onnx`, `prometheus_client` — plus system `libportaudio2` via apt, required or `sounddevice` raises `OSError: PortAudio library not found`). This runs the *entire* wake-word → STT → motion loop locally on the board, no SSH/network hop, no Windows PC involved for the canned-command path — the architecture originally sketched as a "target" is now real and verified:
  - Wake word: same `mira.onnx` model as the Windows build (copied to `~/.local/share/mira-so101/mira.onnx`), same `openwakeword` package (0.4.0, bundles its own base models, unlike the Windows/0.6.0 install which needed `download_models()`).
  - STT: **`hynt/Zipformer-30M-RNNT-6000h`** via `sherpa-onnx` (`OfflineRecognizer.from_transducer`, int8 ONNX, `~/zipformer-vi/` — encoder/decoder/joiner .onnx + a `tokens.txt` generated from the repo's `bpe.model` via `sentencepiece`, since the repo doesn't ship tokens.txt directly). Chosen to replace PhoWhisper project-wide: 30M params vs 769M, and measured end-to-end STT latency **~700-735ms on the board's own aarch64 CPU** for a ~4s clip (vs PhoWhisper's ~1-2s on an RTX 3070) — smaller and faster despite running on much weaker hardware. Verified live, multiple times, with exact-match transcriptions ("mira gật đầu", "mira nhảy") triggering the correct motion with zero alias-table massaging needed.
  - Because BOYAMIC only exposes S24_3LE/2ch/48kHz (see above), audio capture does **not** use `sounddevice`'s stream API directly — it shells out to a persistent `arecord -D hw:CARD=BOYAMIC,DEV=0 -f S24_3LE -c 2 -r 48000 -t raw` subprocess and reads fixed-size raw chunks from its stdout pipe, manually decoding 24-bit LE, keeping only the right channel, and downsampling 48kHz→16kHz with `scipy.signal.resample_poly` before feeding openwakeword/sherpa-onnx (both want 16kHz mono int16). This mirrors the equivalent WASAPI fix needed on Windows (see `windows-pc.md`) — same underlying problem (device won't accept the model's native 16kHz/mono format), different platform-specific plumbing.
  - Motion execution is a plain local `subprocess.run(["mira-robot", "replay", motion, "--yes"])` — no `ssh` invocation at all, since the script already runs on the board.
  - Metrics on `:9103` (kept distinct from the Windows build's `:9101`/`:9102` so both could be scraped by the same Prometheus instance if wired up later — not yet added to `prometheus.yml`).
  - Not yet a systemd service / not yet auto-started — currently run manually via SSH for testing, same `nohup`-survivability caveat as `camera_exporter.py` applies if this is left running unattended.
  - **Wake-word accuracy gap and retrain (in progress, 2026-08-14)**: the openWakeWord "mira" classifier was trained only on synthetic Piper TTS voices, and missed real "Mira" calls from this user often enough to be the pipeline's actual bottleneck. Root fix chosen over lowering the trigger threshold: `voice-control/collect_mira_samples.py` records real positive samples straight from the board's own BOYAMIC mic (same S24_3LE/right-channel handling as `board_wakeword.py`), downsampled to 16kHz mono to match what the classifier trains on. Collected 40 real samples this way. **Bug found and fixed in this script**: it called `arecord -d 1.6` (a fractional duration) — `arecord`'s `-d`/`--duration` only accepts an integer number of seconds and silently exits 0 with "invalid duration argument" on stderr and zero bytes of audio, which the script never checked, so every take looked like pure silence. Fixed by recording without `-d` and reading exactly the needed byte count off a persistent `arecord` pipe (the same pattern `board_wakeword.py` already used) — also now surfaces `arecord`'s stderr so a similar failure can't hide silently again. The 40 real clips were split 34/6 into the RTX 4090's `mira_model/mira/positive_train/` and `positive_test/` (openWakeWord's `train.py` just globs `*.wav` in those directories for feature extraction, so real and synthetic clips mix automatically), `layer_size` was bumped 32→128 in `mira_training_config.yml` for more model capacity, and `train.py --generate_clips --augment_clips --overwrite --train_model` was re-run (`--overwrite` forces feature recomputation to pick up the new real clips; `--generate_clips` is a no-op here since the synthetic clip count already exceeds `n_samples`). Old `mira.onnx` backed up as `mira.onnx.bak_layer32_20260814` before this run. See `gpu-training-server.md` for the training environment.

## Known issues (live)
1. Calibration files (`~/.cache/huggingface/lerobot/calibration/.../my_follower.json`, `my_leader.json`) drift from the physical servos' actual on-chip registers over time. Fixed once this session by reading `bus.read_calibration()` directly off the servo. The follower's calibration was **recalibrated again on 2026-08-14** via LeLab (Windows) + `calibrate_follower.py`, then synced to `my_follower.json` (old one backed up alongside it as `my_follower.json.bak_<timestamp>`) — this was in response to diagnosing that the bundled canned motions (wave/dance/etc., stored as LeRobot-normalized ±100 values) drift in amplitude whenever the calibration they're replayed under differs from the calibration active when they were originally recorded. **Recalibrating alone does not fix this** — replaying `motion_dance` under the new calibration triggered heavy `max_relative_target` safety-clamping (e.g. `shoulder_lift` target -99 clamped down to roughly -32 to -48 across several frames), meaning the canned motions now need to be **re-recorded** under the current calibration to restore correct amplitude. Leader's JSON was separately replaced with a fresh LeLab export earlier — not yet re-verified with the leader physically connected.
2. Second-arm / second-camera enumeration failures recur under load — always check `lsusb` + `dmesg | tail` before trusting a "not connected" error from `mira-robot`. See the board-wide power crash root cause above.
3. VSCode Remote-SSH server processes (`.vscode-server/cli/...`, including a headless Copilot language server) have been observed consuming up to ~1.1GB RSS on this 2GB board. Close the Remote-SSH window when not actively using it.
